观测版本 DSH `0.1.6-alpha.1`；结论一律以真实浏览器截图与 `.verify/` 下的实测脚本为准。

## 1. 「锁定」→「固定」

### 1.1 问题

面板里从未解释过锁定是什么，而它同时影响三件事：Agent 是否敢动这一站、自动重排是否把它当作时间锚点、以及把手能不能拖。
原文案（「已锁定：解锁后可拖动」）只说了第三件事。

### 1.2 统一后的语义

**固定 = 钉住这一站。** 一句话解释：

> 已固定：Agent 不会移动它或改时间，也不能拖动；取消固定后即可调整。

- 行内 chip：`固定`，`title` 为上面这句。
- 把手：固定项的把手显示 🔒 且 `disabled`，`aria-label` 为「已固定，不能拖动」。
- 详情页按钮：`固定` / `取消固定`（原为「锁定 / 解锁」），下方 hint 按当前状态给出一句解释。
- 地点库分组：`已锁定` → `已固定`；照片墙的状态文案改走 `placeStatusLabel`（此前误用行程状态函数，`locked/candidate/excluded` 会显示成「已归档」）。

### 1.3 为什么固定项不允许拖动（修正 v3 的偏差记录）

v3 的偏差记录写过「锁定项允许被拖动位置——它保持自己的时刻并成为后续项的锚点」。0.4.0 实际发布的是**不可拖动**，
v4 把这个选择确认为正确：固定项在 `reflowDay` 里是时间锚点，若允许拖到别处，它会把 14:00 钉在两个 09:00–10:00 的安排之间，
时间轴立刻自相矛盾，并如实抛出一条 `TIME_OVERLAP`。让用户先取消固定、拖完再固定回来，比编造一个"看起来还行"的时间更诚实。

## 2. 时间轴布局

```
┌ 09:45 ●  ┌──────────────────────────────┐ ┌────┐ ⠿
│          │ 故宫博物院（午门入口）  4 小时 5 分│ │ 风 │
│          │ 风景名胜 · 景山前街4号            │ └────┘
│          └──────────────────────────────┘
│  🚶 步行 600 m · 10 分钟
┌ 13:50 ●  … 下一站
```

- **时间轨**：每站一个「时刻 + 节点」，节点取该站类别色（`--trv-tone`）；虚线连接由 `.trv-unit::before` 绘制，
  贯穿该站卡片与**下一段交通**，因此 08:30 → 09:45 是一条连续的线。
- **卡片**：`border-left: 3px` 为类别色带，选中时叠加品牌色内描边（不覆盖色带）；名称、固定 chip、时长（右对齐、等宽数字）
  同一行，第二行是「类别 · 地址」，有告警时第三行用告警色显示最严重的一条。
- **缩略图**：44→42px，垂直居中；照片加载失败时整块消失而不是留灰块。
- **把手**：右侧 22px，透明度 0.45，悬停恢复到 1。

测量（380px 宽侧栏，`.verify/timeline-shot.mjs` 三倍放大截图）：时间轨 46px、卡片可用宽度 258px、缩略图 42px、把手 22px，
地址行在 380px 宽下未出现截断（最长的「京都府京都市东山区清水1-294」完整显示）。

## 3. 拖拽动效

### 3.1 原实现为什么生硬

1. **松手即回弹**：`finish` 先清预览状态再发请求，单位先弹回原位，等 Host 返回后再跳到新位置——两次位移。
2. **命中判定读的是实时 rect**：其它单位正在按 `translateY` 滑动，`getBoundingClientRect()` 跟着动，指针停在临界点时判定的目标在相邻两格间抖动。
3. **每次 `pointermove` 都 setState**：指针事件频率高于渲染帧率，React 反复重渲染整棵时间轴。
4. **没有过渡**：位移是硬跳变。

### 3.2 v4 的四段修复

| 段 | 做法 |
|---|---|
| 开始拖动 | 一次性快照每格的 `top/height`（`metrics` ref），拖动期间命中判定全部用快照，不再读实时 rect |
| 拖动中 | `requestAnimationFrame` 合帧：一帧最多一次 `setDrag`；位移单位 `transition: transform 180ms cubic-bezier(.2,.8,.2,1)`，被拖的单位不参与过渡（零延迟跟手） |
| 松手 | 不再立刻撤预览；把被拖单位吸附到**落位槽**（由快照几何算出，而不是手停在哪里），并给它 170ms 缓入 |
| 到位 | Host 新顺序到达的那一帧同时丢掉预览位移，并在该帧关掉过渡（`.trv-timeline-committing`），因此画面零变化；2.5s 兜底计时器防止请求失败后卡在预览态 |

### 3.3 实测（`.verify/interactive-panel.mjs`，真实指针事件 + 真实 React）

拖第 1 站向下两格，读数为其相对静止位置的位移（px）：

| 时刻 | DOM 顺序 | 位移 | 列表 class |
|---|---|---|---|
| 拖动中 | a1 b2 c3 d4 | `+186`（跟手）`-85`（让位）`0 0` | `trv-timeline-dragging` |
| 松手后 90ms（Host 未返回） | a1 b2 c3 d4 | `+170`（已吸附到槽位）`-85 -85 0` | `…-dragging …-committing` |
| Host 返回后 | b2 c3 a1 d4 | `-6 -6 +247 +78` | 已清空 |

第三行与第二行的差值恰好等于重排后横幅（「已按停留时长重排」）插入带来的整体下移，说明**到位帧没有额外位移**；
随后第二次拖动（把末尾一站上移一格）结束时所有 class 已清空、位移与最终布局一致——预览态不会残留。

## 4. 照片补全

- 新增 `POST /refresh-places` 与模型工具 `travel_place_refresh`：对**没有 `photoUrl`** 的地点，用其名称在行程目的地城市重新检索 POI，
  匹配规则为「先按 `providerPlaceId` 精确命中，其次按**完全同名且带图**命中」；两者都不中则记入 `unmatched`，绝不猜。
  （原实现只处理"有 providerPlaceId 但没照片"的地点，手工添加的地点永远补不上。）
- 地点库顶部在有缺失时出现「还有 N 个地点没有照片」+「补全照片」按钮；补全后重新拉取视图，照片墙自动出现。
- 失败/为空也如实反馈：「已检查 N 个地点，没有可补全的照片。」
- 照片仍是高德 CDN 的 http 链接：在 `http://127.0.0.1:3080` 下可直连；若将来从 https 打开，需要 Host 侧代理（未做）。

## 5. 常驻的重算入口

提示条（`ReflowBar`）只是**一次性提示**：它曾把唯一的重算入口放在自己身上，用户点「我知道」后入口就永久消失。

- 日头新增常驻 chip「交通待重算」：只要当天存在 `stale` / 非 `fresh` 的 leg，或相邻站之间缺 leg，就一直显示。
- 点 chip 打开底部「这一天的交通」抽屉：说明为什么会出现待重算、给出「用高德重算这一天」（走 CLI，不花对话额度）与「让 Agent 复核」。
- 提示条里的按钮改为「重算这一天交通 / 让 Agent 复核 / 稍后」——「稍后」只关掉提示，入口在日头。

## 7. 偏差与未做

- 跨天拖动（把 D2 的一站拖到 D1）仍未做：需要新的 Host op 与跨天下拉落点。
- 地点库没有分类筛选；照片墙超过约 20 个地点后会偏长。
- PDF 导出仍未设计。
- 详情浮窗的尺寸是**一个**记忆值：窄栏当高度用、宽栏当宽度用。够用，但不是两套独立记忆（见 §8）。
- 详情浮窗固定锚在右下角，不能拖动位置（只能改大小）。

## 8. 详情面板：浮层 → 停靠 → 可调整大小的浮窗（0.6.0 → 0.6.1）

### 8.1 问题（0.5.0 实测）

详情卡片是 `.trv-sheet-bottom` 绝对定位浮层：宽栏时固定 `width: 320px`、`max-height: 70%`，右下角压在时间轴上——
**被点开的这一站，正好被它自己的详情挡住**；尺寸写死、不能调；窄栏同样是浮层。

### 8.2 第一次尝试（0.6.0，被否）

改成「参与布局」：窄栏停靠在时间轴下方、宽栏是右侧一列，内边缘可拖拽并记住尺寸。实测（`interactive-panel.mjs`）：
窄栏 `y=507 h=241`、宽栏 `x=549 w=241` 而时间轴列缩到 525——**代价是时间轴变窄**，用户判断不如悬浮窗，遂回退。

### 8.3 最终方案（0.6.1）

- 详情恢复为**绝对定位的浮窗**（`.trv-detail`）：窄栏贴底通栏，宽栏是右下角侧窗
  （`width: clamp(240px, 记住的值, 70%)`，高度按内容自适应、上限 82%）。
- 内边缘（窄栏顶部 / 宽栏左侧）仍是 12px 拖拽把手，尺寸写入 `localStorage['skillre-travel:ui'].detailSize`，CSS 再 clamp。
- 时间轴在两档布局里都保持全宽：实测宽栏 `main.w = 778`，浮窗 `x=586 w=302` 覆盖其上但不改变列宽；窄栏整宽浮窗 `h=302`。
- 「固定」不再在按钮下面印一段解释：含义移到按钮 `title`（固定 / 取消固定 各一句）。

### 8.4 顺手修掉的潜伏 bug

`.trv-body` 改为不整体滚动后，滚动交给 `.trv-col-main`；拖拽时的贴边自动滚动读的正是 `.trv-timeline` 的父元素，
它此前**不是滚动容器**，那段代码一直是空操作。

## 9. 照片按需补全（0.6.0）

0.5.0 的补全只能整库跑（地点库里的按钮），而用户先看到的其实是**详情里没有图片**。

- `POST <prefix>/refresh-places` 与 `travel_place_refresh` 新增可选 `placeId`：只查这一个地点。
- 详情面板在「地点没有照片 + 允许下发照片」时**自动查一次**（每个地点只自动查一次，失败不重试成环）；
  查询中显示「正在向高德补全照片…」，查不到或出错则显示具体原因 + 「再查一次」。
- 视图新增 `photos: boolean`：`ui.placePhotos: 'off'` 时客户端不显示任何照片界面，也不发起查询——配置关闭即零调用。
- 头部信息行新增「缺 N 张照片 · 补全」：时间轴缩略图需要整库补全，这个入口比藏在「地点库」里更容易遇到。

## 10. AMap CLI 的「超时地板」（0.6.1）

### 10.1 症状

用户反复反馈「图片加载不出来 / 很慢」：详情一直停在「正在向高德补全照片…」。

### 10.2 定位过程

| 观察 | 结论 |
|---|---|
| 交互式与模型工具两条路径，未命中缓存的 POI 查询都是 **~98 秒** | 与调用方无关，问题在 CLI 公共路径 |
| shell 里 `amap-gui searchPOI` 只要 **0.4 秒** | 不是 CLI、不是容器、不是网络 |
| 缓存命中的查询 **1 秒内**返回 | 慢的只有真正执行 `exec` 的那一步 |
| `98s ≈ 2 × 45s + 8s`，而 `commandTimeoutMs = 45000` | 每次 exec 都至少等满预算；一次查询含 `ensureReady` + `searchPOI` 两次调用 |
| 前一天整库补全 12 个地点约 18 分钟 | 12 × 2 × 45s 完全吻合 |

根因在 `src/host/amap/exec.ts`：

```ts
const timeout = delay(request.timeoutMs).then(() => { timedOut = true; controller.abort() })
// …
finally { await timeout }   // ← 把预算当下限来等
```

`finally` 里的 `await timeout` 让**每次调用都必须等满预算**：CLI 0.4 秒答完，调用方仍要等到 45 秒的定时器触发。

### 10.3 修复

- 预算只作上限：子进程一结束就返回；定时器到点时若调用已结束则**什么都不做**（`settled` 守卫，避免对已退出的进程发 abort）。
- 定时器仍自行结算、不阻塞任何东西；到点早于子进程结束时行为不变（abort + `timedOut: true`）。
- 两条回归测试：`returns as soon as the child exits, without waiting out the timeout`（定时器永不触发，调用仍必须返回）、
  `leaves a finished call alone when its timer finally fires`（事后触发不得终止任何东西）。

### 10.4 影响

单次 POI 查询 98s → **约 1s**；整库 12 个地点补全约 18 分钟 → **约 15s**；`travel_day_rebuild_legs` 每段路线同样少等 45 秒。
该 bug 自 0.1.0 起就存在，只是被「高德本来就慢」的印象掩盖了。

## 15. 日期栏放不下且不能滑动（0.7.3）

### 15.1 原因

宽栏的日期栏 `.trv-rail` 只有 `flex-direction: column`，**没有 `overflow`**；而它的父级 `.trv-body` 在 0.6.1 之后改成了
`overflow: hidden`（为了让详情浮窗不再影响列宽）。于是 14 天的行程里，D12 之后的日期被裁掉且**永远够不到**。

### 15.2 修复

- `.trv-rail` 加 `min-height: 0; overflow-y: auto; overscroll-behavior: contain; scrollbar-width: thin;`——日期栏自己滚动。
- 日期项改为**单行**（`D1 09-24`，`align-items: baseline`，内边距 4px）：行高从约 45px 降到 27px，
  14 天从 630px 降到约 420px，多数窗口里可以直接放下，不必滚动。
- 切换日期时把当天**滚入视野**（手写 `scrollTop` 计算，不用 `scrollIntoView`——后者会连带滚动整栏）。

### 15.3 实测（`.verify/rail-scroll.mjs`，用你的 14 天行程）

| 项 | 结果 |
|---|---|
| 日期项 | 14 个，单行 27px |
| 内容高 / 可见高 | 422px / 284px（该测试窗口较矮，故仍需滚动） |
| `overflow-y` | `auto` |
| 滚到底后最后一个日期 | 可见且可点（`elementFromPoint` 命中） |

## 14. 全程地图：连续路线 · 水滴标记 · 全程不列景点（0.7.2）

### 14.1 症状

14 天的自驾行程（北京→西安→成都→丽江→大理→昆明→贵阳→西江→凤凰→武汉→郑州→北京）在「全程」视图里：

1. **连线不全**——只有部分天有虚线；
2. 每一站都顶着「起/终」方块标签，十几个起点十几个终点；
3. 大图模式下底部还列着「景点」，切到全程后既没有意义又显示不全。

### 14.2 根因

- 地图是**按天各画一条折线**，只连该天自己的站点。而这条行程里 d2/d3/d4/d7/d9/d10/d13/d14 每天只有一个点（当天的落脚城市），
  一个点画不出线 —— 于是整条路线看起来断成一截一截。
- 标记文案写死为「当天的第一个＝起、最后一个＝终」，天数一多就变成一片「起」「终」。
- 底部景点条只判断了大图模式，没有判断范围。

### 14.3 修复

- 新增 `buildRouteSegments(groups)`：每天的折线**延伸到下一天的第一个点**，于是「单点天」也有线，整条路线连续；
  颜色仍按天取，图例照旧解释 D1…D14。示意地图（AMap 不可用时的回退）同样改用该函数绘制。
- 标记改为**水滴形**（圆形头 + 同色小尾巴，颜色经 `--trv-pin` 传入），标签改成**当天内的序号**（1、2、…），不再有起/终。
- 「全程」不再显示底部景点条：`tier === 'full' && range === 'day'` 才显示；全程保留色板图例。

### 14.4 实测（`.verify/trip-map-14d.mjs`，用你那份真实行程的坐标）

| 项 | 结果 |
|---|---|

### 13.1 原因

`.trv-head` 是 `position: relative`，而它只有 header 那么高（约 56px）。下拉面板 `.trv-sheet-top` 的

## 12. 免容器的照片来源：高德 Web 服务 API（0.7.0）

「不弹窗」的彻底解法不是「先问一句」，而是**换一条不需要容器的数据通道**。

### 12.1 为什么可行

高德账号可以持有多种 Key：JS API Key（浏览器画图用）、**Web 服务 Key（服务端 REST 用）**。后者直接回答 POI 查询：

```
GET https://restapi.amap.com/v3/place/text?key=…&keywords=…&city=…&extensions=all
GET https://restapi.amap.com/v3/place/detail?key=…&id=<providerPlaceId>
```

`place/text` 带 `extensions=all` 时返回 `photos[]` 与 `tel`；`place/detail` 按 POI id 精确取回同一个 POI（含 `photos[]`）。
两者都是 HTTPS，**不碰 CLI、不碰容器、不会开窗**。用户机器上 `~/.zshrc` 里已有 `AMAP_REST_KEY`，实测直接可用。

### 12.2 实现

- 新增 `src/host/amap/rest.ts`：`searchPoisOverRest`（关键词搜索）与 `getPoiByIdOverRest`（按 id 详情），
  统一在一个 `callRest` 上做**超时、串行节流（默认 350ms）、QPS 限流重试（infocode 10021，最多重试 2 次）**。
- 新增配置 `amap.restKeyRef`（默认引用名 `AMAP_REST_KEY`）。它解析成功时：
  - `refreshPlaceFacts` 走 REST，**不调用 CLI**（因此 `allowStart` 无意义）；
  - 视图新增 `photoLookup: 'direct' | 'container'`，客户端据此决定「自动查」还是「先问一句再启动容器」。
- 匹配顺序仍是**先按 POI id、再按完全同名**；REST 的 id 详情路径让「名字被 Agent 改写过」的地点也能命中
  （例如「故宫博物院（午门入口）」存的 `B0FFKL520U` 实际是「故宫博物院检票处」）。
- Key 只在 Host 进程内使用，永不下发浏览器；它会出现在请求 URL 里（高德接口如此设计），因此不进日志、不进工具返回。

### 12.3 实测（用户真实行程，只读回放）

| 项 | 结果 |
|---|---|
| 缺照片的地点 | 11 |
| 通过 REST 补到照片 | **10**（其中 8 条走 POI id 详情，2 条走关键词搜索） |
| 未补到 | 1 条：`酒店锚点（建议：王府井/东单/崇文门）` —— 不是真实 POI，本就没有照片 |
| 是否调用 CLI / 是否弹窗 | **完全没有** |
| QPS | 未限流（节流生效；未节流时实测会撞 `CUQPS_HAS_EXCEEDED_THE_LIMIT`） |

### 12.4 回退

没有 Web 服务 Key 的部署仍然可用：`photoLookup: 'container'`，行为回到 0.6.2——容器在线时自动查，离线时给出「启动高德并补全」按钮。

## 11. 照片查询不再擅自启动高德窗口（0.6.2）

### 11.1 现象与原因

用户问：「为什么我一点开地点详情、获取图片的时候，会把高德的 GUI 打开？」

高德 CLI 是**驱动一个正在运行的 JSAPI 容器**来回答查询的（POI 搜索、路径规划都一样），
所以 `AmapGateway.ensureReady()` 在容器未运行时执行 `amap-gui start` —— 而 `start` 会打开高德地图窗口。
打开详情触发的照片查询同样走 `ensureReady`，于是「顺手补一张图」把一个桌面窗口带了出来。

### 11.2 规则

**启动容器必须是调用方明确要求的**：`ensureReady(signal, { allowStart })`

| 调用方 | allowStart | 理由 |
|---|---|---|
| 模型工具（`travel_place_search` / `travel_route_plan` / `travel_day_rebuild_legs` / `travel_place_refresh` / `travel_map_focus`） | 允许 | 都是显式动作，用户/Agent 明确要地图事实 |
| 面板「重算这一天交通」「在地图中打开当天」 | 允许 | 按钮本身就是要用地图 |
| 面板打开详情时的静默照片查询 | **不允许** | 只是锦上添花，不该弹窗 |
| 面板「补全照片」（头部 chip / 地点库按钮） | 允许 | 标签已写明会启动高德 |

- 容器未运行且不允许启动时，网关抛新的稳定错误码 `AMAP_NOT_RUNNING`；`POST /refresh-places` 捕获它并返回
  `{ ok: true, needsStart: true, checked: 0 }`（不是错误，而是前置条件缺失）。
- 客户端只在 `/state` 报告容器 running 且 mapReady 时才自动查询；否则详情卡片显示
  「高德地图容器未运行；补全照片要先启动它（会打开高德地图窗口）。」+ 按钮「启动高德并补全」；
  头部 offer 的标签同时变成「缺 N 张照片 · 启动高德并补全」。

### 11.3 测试

`POST /refresh-places` 三条新用例（默认 `allowStart: false`、`start: true` 才放行、容器未运行时返回 `needsStart`）
与客户端两条（容器在线才自动查、离线时给按钮且不自动查）。

# 旅行规划工作手册

## 0. 先理解这件事的性质

这是一个**结构化旅行工作台**，不是一次性生成攻略的聊天机器人。

- 唯一事实源是 Trip Project（`<工作区>/.travel/projects/<tripId>/trip.json`），**不是对话记录**。用户会和你反复改同一份项目，跨会话也还在。
- 右侧栏是用户看这份项目的地方（行程 / 地图 / 地点 / 提醒）。你写进去的东西会立刻出现在那里，所以不要用聊天消息"演示"行程。
- 事实查询、持久化、时间重算、告警都由工具和代码完成；你负责理解意图、取舍和解释。**不要心算路线和里程，去查。**
- 高德不提供营业时间、评分、实时票价、天气。这些要么问用户，要么显式标成待确认——编造一条"通常 9 点开门"就是这份规划最严重的缺陷。
- 用户要的是**能执行**的行程：到了现场拿得出地址、知道下一站在哪、知道哪一步还没落实。

## 1. 每次改动都走同一个循环

```
travel_project_read   →   travel_project_patch   →   travel_itinerary_validate   →   讲给用户
      （拿 revision）        （写，带 expectedRevision）      （确定性校验）            （摘要 + 告警 + 下一步）
```

- **改之前必读**：`revision` 决定你能不能写成功，`view` 里有每天的项、时刻、交通段与告警。不读就写 = 覆盖用户的改动。
- **`expectedRevision` 一定要回传**上一次读到的 revision。注意：会落盘的工具（含 `travel_place_search{add:true}`、`rebuild_legs`、`validate` 之外的写操作）都会把 revision 推高——**每次 patch 前重新读一次**，不要用十几步之前的旧值。
- **`revision` 不是自增计数，是并发保护**：拿到 `REVISION_MISMATCH` 说明有人在你读之后写过，重读再改即可。
- 写完看 `applied[]` 和 `rejected[]`：**patch 不是事务**，合法的 op 已经落盘、revision 已 +1，被拒的 op 只在 `rejected[]` 里。被拒后要么改参数重试，要么告诉用户为什么做不到——不要假设整批回滚了。
- **报错 ≠ 没写**：`travel_project_create` / `travel_project_patch` 报错时，先用 `travel_project_list` 或 `travel_project_read` 确认这次写入是否已经落盘，再决定是重试还是换写法。直接重试容易撞上"同标题同日期已存在"或重复 id，把一次小故障变成需要人工清理的烂摊子。
- **验收是机械门槛**：`travel_itinerary_validate` 的 **error 必须为 0** 才能说"行程就绪"。交付摘要固定带一行：`自查：修复 N 项；遗留 M 项（逐条列出）`。warning 不能藏起来，info 也要说明它是什么。

## 2. 从一句需求到一份行程

### 2.1 先建简报，然后立刻开工

从对话里抽取：出发地、目的地、起止日期、同行人、预算、兴趣、节奏、必去、避开、是否频繁换酒店、**住宿区域**。**只追问真正阻塞规划的项**，一次问完，不要挤牙膏式三连问。合理默认可以自行采用（节奏 `balanced`、货币按用户所在地、市内默认 `transit` + `walking`、每天 09:00 起排），然后在第一次汇报里说明你默认了什么，让用户纠正。

```
travel_project_create{ title, startDate, endDate, destinations, travelers, pace, interests, avoid, budgetLimit }
```

注意：`endDate` **含当天**；天数上限 30 天；同标题同出发日期不能建两次。

### 2.2 多城行程：先交骨架，等确认

涉及 **≥2 个城市**时，不要直接排逐日细节。先用一次回复交"骨架"并停下来等确认：城市顺序、每城住几晚、城际方式与真实里程/时长（`travel_route_plan` 查，别估）。**城市顺序是用户最容易拍板、也最该拍板的一步**——排完 30 天再改顺序等于全盘返工。用户确认后再落 items（顺序定下来的关键日期可以用 `set-item-lock` 钉住）。单城行程跳过这一步。

### 2.3 地点要搜出来，不要想出来

`travel_place_search` 走的是真实高德 POI。按主题分批搜（"西湖""灵隐寺""龙井村"），不要搜"杭州好玩的地方"这种模糊词；关键词搜索带上 `city`；用周边搜索（`centerLongitude` / `centerLatitude` / `radiusMeters`）找"以酒店为中心 2 公里内的咖啡馆"。

- 搜到的候选加 `add: true` 入项目地点库；同一个 POI 再搜一次会因 id 重复被拒，这是去重而不是错误。
- 用户提到的具体地点（"我要去清水寺"）也要搜一遍再入库——只有库里的地点才能被排进行程。
- **给检索一个预算与停止规则**：总次数约 `2 × 天数`；同一关键词重试不超过 2 次；仍然没有结果就把它放进待确认清单，**不要换措辞硬凑、更不要凭记忆补一个地点**。找不到就停下来说找不到，这是这份 skill 最看重的纪律。
- 地点 `status`（candidate / planned / excluded / locked）只影响右侧栏的分组展示，**不参与任何校验**。真正"不能动"的语义是 item 的 `locked`（见 §4）。
- 照片和电话用 `travel_place_refresh` 补；它可能启动高德容器（会弹窗），不需要时别频繁调用。

### 2.4 编排：先聚类，再排时间

一天的地理形状比景点数量重要。经验值（不是插件硬线）：同一天的地点应落在**步行 1.5 公里或车程 20 分钟**的范围内；每天主要停靠 relaxed ≤3、balanced 3–4、intensive 5+；单日纯在途时间尽量 ≤2 小时。判断依据和更多规则见 `references/itinerary-craft.md`。

```
travel_project_patch{ expectedRevision, ops: [
  { kind:'add-item', dayId:'d1', item:{ id:'d1-i0', placeId:'amap-xxx', plannedDurationMinutes:120, notes:['[锚点] 提前预约，进门右转取票','地址：xxx路 1 号'] } },
  { kind:'set-item-time', dayId:'d1', itemId:'d1-i0', startAt:'2026-10-02T09:30' },
  ...
]}
```

- `item.id` 自己起名，稳定且唯一即可（习惯写法 `d1-i0`、`d1-i1`）。
- **每天的第一个安排必须给 `startAt`**，否则重排时这一天没有起点，时间不会动。
- 两站之间给 `plannedDurationMinutes`（停留时长）；不要手算结束时刻，交给重排。
- **备注一次写全**：`notes` 只在 `add-item` 时能写，事后补只能删掉重建（还会丢掉那一段交通）。现场真正要用的东西现在就写进去——地址、电话、预约信息、以及下面这些标记：
  - `[锚点]`：已经订好/必须保留的（与 `locked` 配合，锁是机器语义，标记是给人看的）
  - `[可跳过]`：时间不够时第一个牺牲
  - `[雨天替代→dX]`：室内备选（方案分支 `scenarios` 目前不可用，备选只能这样表达）
  - `[闭馆备选→dX]`：同一个景点闭馆/满员时的**同区原地补位**（与"雨天换室内"不是一回事）
  - `[并行]` / `[缺席]`：当天有人分头行动或不在场时，标出各自的轨道与汇合点（`travelers` 没有逐日在场字段，只能写在备注里）
- 排完顺序用 `{ kind:'reflow-day', dayId:'d1' }` 让代码按"停留时长 + 已测交通"重算时刻。**`add-item` / `move-item` / `set-item-time` 都不会自动排时间**，想改时刻必须显式 reflow（或 `reorder-day` 带上完整顺序）。

### 2.5 交通段：先查，再落盘

```
travel_day_rebuild_legs{ dayId:'d1', mode:'transit', city:'杭州' }   # 当天相邻站点逐段查真实路线并落盘
```

- 公交必须给 `city`，跨城交通不能伪装成本地公交。
- **一天只吃一个 `mode`，真实行程是混合的**：先按 `transit`（或驾车）刷一遍，再把明显该走路的短段（<1.5 km）用 `travel_route_plan(mode:'walking')` 查出来、`set-leg` 覆盖——否则会出现"400 米也坐地铁"的荒唐数字。
- `travel_route_plan` 只查询不落盘，适合"帮我看看这两点怎么走"；要写进行程用 `rebuild_legs`。
- **跨城段至少比两种方式**（如驾车 vs 公交/骑行可行时），把两组里程与时长都讲给用户再落最终 leg。
- 里程与时长**不含往返住处**：如果用户给了住宿，单独查"住处 ↔ 当天首站/末站"并写进交付摘要，别让用户以为这就是全天的移动成本。

### 2.6 收尾

`travel_itinerary_validate` → error 清零、warning 逐条解释 → `travel_project_export{ format:'markdown' }` 得到行程单（落在 `exports/itinerary.md`）。

**导出件是薄的**：每行只有 时间 · 地点名 · 类别 · 停留时长（不含地址、电话、备注）。所以交付时必须补一份"现场信息"：把关键地点的地址、电话、预约号列在回复里（或确认它们已经写进 item 的 `notes`，右侧栏会显示）。同时说明：哪些数字是查来的、什么时候查的；哪些是估算；哪些还需要用户确认。

## 3. 赶路日：一天只有路，也是一天

跨城那天常常没有景点。这时**不要**用 leg 硬凑，用 `travel_day_set_transit` 把"移动"本身记下来：

```
travel_day_set_transit{ dayId:'d4', fromPlaceId:'amap-城市A', toPlaceId:'amap-城市B', mode:'driving' }
```

- **端点用 `placeId`，不要只给城市名**：只给名字的端点会被地理编码，而"成都"这种词可能被解到完全错误的位置（实测解到北京，于是算出 1957 公里的"跨城"）。没有城市锚点就先 `travel_place_search` 搜一个再传 id。
- `plan` 默认 `true`：你传的里程和时长**会被高德结果覆盖**。要保留自己写的数字（例如用户明确说"723 公里"）就传 `plan:false`，此时会标成「按标题估算」。
- 转场属于"天"，不计入站数与停留，但计入里程与当日行车时长，而且会让"单日驾驶偏长"的告警生效。
- 决策规则：**相邻城市之间当天来回 >2.5 小时**（经验值），就把它整段留成赶路日；不要上午跨城、下午还排三个景点。
- 当天标题里的里程与实际不符时（标题写 150 km、真实 136.8 km），主动问用户要不要把标题改成真实值——标题是用户最先看到的一行。
- 没有转场、只有标题里写了"西安 → 成都｜723km"的赶路日，右侧栏可以用「补全 N 天路线」一次性算真实路线——那是面板的动作，你负责的是 `travel_day_set_transit`。

## 4. 锁定与 revision：用户的手和你的手

- 用户可以在右侧栏拖拽、改时、锁定。**锁定项是锚点**：不能移动、不能改时、不能删除；重排时它不动，其余项绕着它排。
- 锁定还会**连带锁住它所在的天**：当天有任意锁定项时，`set-day-title` 和 `remove-day` 会被拒（`ITEM_LOCKED`）。要改标题，先确认那天没有锁定项。
- 解锁用 `{ kind:'set-item-lock', dayId, itemId, locked:false }`——这是唯一能解锁的操作。
- 提醒用户：他会经常手动改；你每次都要先读再写，别把他刚拖好的顺序盖掉。

## 5. 插件知道什么、不知道什么

| 你能查到的（真实数据） | 插件不提供的（不要编） |
|---|---|
| 地点名称、地址、坐标、类别、电话、照片 | 营业时间、是否闭馆、是否需要预约、放票时间 |
| 步行/公交/骑行/驾车距离、时长、驾车途经点 | 评分、排队时长、人流 |
| 跨城路线的里程、时长与路径 | 门票价、实时票价、酒店房价 |
| 确定性告警（重叠、缺路线、过载、预算、过期） | 天气、季节景色、临时封路 |

处理方式：

- **问用户，或显式标注**。凡涉及营业时间、票价、预约窗口、天气的判断，在 `notes` 与回复里必须带 `⚠ 待确认：<事项>（需你确认 / 到场确认）`；数值未知就写 `—`，**不要写一个看起来精确的数字**。
- **预约制景点是可行性问题，不只是提醒**：问清"放票时间、有没有当日票"。**放票日晚于行程日 ⇒ 这个点不能当锚点**，改排备选把窗口写进 notes。
- **时区要声明**：项目默认 `Asia/Shanghai`。出境行程必须在回复里写明"以下时刻均为当地时间"；时差 ≥6 小时时，首日不排主要景点。
- **住宿是锚点不是备注**：用户给了住处就把它当作当天的首/末站来看距离（见 §2.5）。
- 预算说明口径：住宿/餐饮/门票/市内交通各多少、人均还是总额、含不含大交通。只填 `limit` 不填 `estimatedTotal`，插件只会给一条 info 级的"预算未知"，不会替你算超支。
- 提前量按经验值倒推（国内机票约 30 天、跨城高铁约 15 天、限流景点约 7 天、网红餐厅约 3 天），**一律标经验值并提醒以官方放票窗口为准**。
- **不要说"插件会按它约束"**：`preferences` 里只有 `pace`（`relaxed` 时）与 `preferredModes[0]` 会真的改变插件行为；`avoid`、`interests`、`maximumWalkingMinutesPerLeg` 以及"同行人不能久走""需要无障碍"这类要求，插件**不读、不校验、不重排**。对用户只能说"**我已按这个设计**"，执行责任在你，不在工具。

## 6. 怎么跟用户说话

一次交付至少包含这五样，缺哪样用户都得再问一遍：

1. **变更摘要**：改了哪一天、动了哪些点、里程/时长怎么变、revision 是多少。不要复述整份行程——右侧栏有。
2. **每日强度**：用现有数字给一行 `强度：中（停留 5h10m + 在途 1h20m，4 个停靠）`，让用户一眼看出哪天会累。
3. **告警翻译**：把 `DAY_OVERLOADED` 说成"这一天排了 11 小时（含 1 小时 40 分在途），建议把 XX 挪到第二天"，并给出可选动作。
4. **待确认清单**：营业时间/预约/票价/天气，逐条写清"需要你确认什么、什么时候之前确认"。
5. **自查行**：`自查：修复 N 项；遗留 M 项（逐条列出）`，以及数据来源与新鲜度（哪些是今天查的、哪些是估的）。

其他：需要用户看某一天时用 `travel_map_focus{ dayId }` 把地图聚过去；主动给 2–3 个下一步选项，而不是问"还需要什么"。

**遇到取舍就摆选项，不要自己闷头砍**：两个必去撞车、时间不够、放票窗口互斥时，给 A / B 两案（各写清代价）+ 一个默认推荐，让用户回一个字母就行。模板与取舍顺序见 `references/trip-design.md` §5；砍单顺序见 §2。

## 7. 多行程与切换

- 省略 `tripId` 时按「会话选择 → 工作区默认 → 最近更新」解析；**多个行程并存、或你在子会话/并发环境里工作时，"最近更新"很可能不是你要的那份**。此时**每一次调用都显式传 `tripId`**——尤其是 `travel_project_export` 与 `travel_itinerary_validate`，它们会把结果写到被解析出来的那一份里。
- 用户按名字提到另一个行程（"上次那个京都的"）时，先 `travel_project_list` 找到 id，再 `travel_project_select`。用 `asDefault: true` 才会改工作区默认。
- 一个工作区可以放多份行程；数据全在 `<工作区>/.travel/` 下，形状见 `references/data-model.md`。

## 9. 这份 skill 的红线

1. 不编造高德没给的事实（营业时间、评分、票价、天气）；不确定就写 `⚠ 待确认`，数字未知写 `—`。
2. 不做心算里程——`travel_route_plan` / `rebuild_legs` / `set_transit` 才是数字来源。
3. 不跳过读就写；不回传过期的 `expectedRevision`；多行程时显式传 `tripId`。
4. 不移动、不删除、不改用户锁定的安排；也不要绕过锁定语义去改它所在的那天。
5. 不为让告警变绿而假装改好——**error 没清零就不说"行程就绪"**，修不了的如实列为遗留项。

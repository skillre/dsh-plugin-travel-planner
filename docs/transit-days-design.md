## 一、你指出的问题，在数据里长这样

`TripDay` 现在只有两样东西：`items[]`（地点+时间）和 `legs[]`（**同一天内**两项之间的一段路，`fromItemId`/`toItemId` 都是本天的 item）。所以"今天整天在路上"这件事**没有地方放**，只能用地点去顶。你的行程里 14 天是这样顶出来的：

| 天 | 标题 | 现在的 items | 记录的 leg | 实际是什么 |
|---|---|---|---|---|
| D1 | 北京 → 西安｜赶路 1,077km | 天安门广场@12:00、回民街@**次日** 00:30 | 1077km / 12.6h | 纯赶路：出发地、到达地被当成两个「站」 |
| D2 | 西安 → 成都｜翻秦岭 723km | 宽窄巷子@18:30 | **无** | 赶路 + 到达；里程只在标题里 |
| D3 | 成都 → 丽江｜到站 821km | 丽江古城@17:30 | **无** | 同上 |
| D4 | 丽江｜婚纱照拍摄日 | 丽江古城@08:00 | 无 | 真正的游玩日 |
| D5 | 丽江 → 大理｜175km | 4 站（含 洱海公园 ×2） | 175+7+6km | 转场 + 游玩 |
| D6 | 大理｜洱海完整一天 | 3 站 | 13km | 游玩日 |
| D7 | 大理 → 安顺｜738km 长途转移 | 黄果树景区@08:00、黄果树景区@19:00 | **0km** | 纯赶路：同一地点放两次当锚点 |
| D8 | 黄果树 → 西江｜295km | 3 站（西江 ×2） | 335km+0 | 转场 + 游玩 |
| D9 | 西江 → 凤凰｜285km | 3 站（凤凰 ×2） | 285km+0 | 同上 |
| D10 | 凤凰 → 武汉｜674km | 3 站（黄鹤楼 ×2） | 674km+0 | 同上 |
| D11 | 武汉｜完整一天 | 3 站 | 7km | 游玩日 |
| D12 | 武汉 → 洛阳｜573km | 龙门石窟 **×3** | **0km** | 纯赶路：同一地点放三次 |
| D13 | 洛阳 → 石家庄｜526km | 龙门石窟、**石家庄站** | 527km/6h | 转场 + 到达；车站被当成一个「站」 |
| D14 | 石家庄 → 北京｜291km | 天安门广场@07:30 | **无** | 赶路 + 到达 |

从这张表能直接数出四个症状：

1. **5 天（D2/D3/D7/D12/D14）标题写了里程却没有 leg** —— 于是行程页只能写「跨城交通未记录 · 里程按当天标题估算」，这不是例外，是常态（`buildTransfers` 那段从标题猜数字的代码就是为它写的）。
2. **5 天出现重复锚点**（D7 黄果树 ×2、D8/D9/D10 ×2、D12 龙门石窟 ×3）—— 这些 item 存在的唯一理由是"这一天得有个地点"。
3. **到达点、出发地、车站都被当成「站」**：D1 的 天安门广场（出发地）、D13 的 石家庄站（到达点）会带着缩略图、停留时长、站数进入统计。
4. **纯赶路日被判成"超载"**：`dayTotalSeconds` = legs 时长 + 停留，D1 = 12.6 小时 > 10 小时上限，你现在的行程里正好挂着这条告警：`第 1 天总耗时约 12.6 小时，超过 10 小时上限。`（建议动作还是「减少一个安排 / 改用更快的交通方式」——对一条 1077 公里的自驾完全不适用。）

另外两条是同一根因的延伸：

- **跨午夜没有归宿**：D1 到达 04:30 记在"前一天"的 item 上，读起来是 D1 上午 12:00 出发、次日 04:30 到；时间重叠校验也按 item 算。
- **地图把"路过/抵达"画成"游玩的站"**：同一个水滴、同一套语义（这正是你上一轮让所有点变水滴后更明显的地方）。

**根因一句话**：这个领域里只有「停留（item）」和「同一天两项之间的路（leg）」，缺了**「转场」**——一天里那段"不为了让谁停留、只为了换城市"的移动。

## 二、目标

1. 一天可以**只有赶路**、没有任何地点，而且是完整的一天，不被当作"还没安排"。
2. 转场本身携带里程、时长、出发/到达时刻、路线来源与新鲜度，能参与告警、统计、地图和导出。
3. 转场的**端点不必须是"要游玩的地点"**：可以只写「西安」这样的名字；有对应地点时用它的坐标。
4. 跨午夜的到达有地方放（`arriveAt` 落在次日），不必再造一个次日 item。
5. 已有的行程**不用重录**：能从现有的"标题 + 相邻天的端点"一键升级，升级后再用高德把它算成真实路线。

## 三、方案：把「转场」做成一等公民

### 3.1 数据（`src/domain/trip.ts`，schemaVersion 1 → 2）

```ts
/** 转场的一端：有地点就用它的坐标，没有就只有一个名字。 */
export interface TransitEnd {
  readonly placeId?: PlaceId      // 行程地点库里的地点（有坐标/照片时）
  readonly label: string          // 永远有：给读的人看的「西安」
}

export interface TripTransit {
  readonly id: string
  readonly from: TransitEnd
  readonly to: TransitEnd
  readonly mode: TravelMode
  readonly distanceMeters?: number
  readonly durationSeconds?: number
  readonly departAt?: string      // ISO，可落在当天
  readonly arriveAt?: string      // ISO，**允许落在次日**
  readonly tollsYuan?: number
  readonly steps: readonly RouteStep[]     // 复用现有 RouteStep
  readonly freshness: RouteFreshness       // fresh | stale | failed
  readonly source: SourceStamp | { readonly provider: 'title'; readonly fetchedAt: string }
}

export interface TripDay {
  // …现有字段不变
  readonly transits?: readonly TripTransit[]   // 新增；0..n，常见是 0 或 1
}
```

要点：

- **一天可以多段转场**（上午 A→B、下午 B→C），UI 按顺序渲染；绝大多数行程只用一段。
- `RouteLeg`（同一天两项之间的路）**完全不动**：市内几站之间的移动仍然是 leg。转场是"换城市"那一层，leg 是"到了以后怎么逛"那一层。
- 端点**不是 item**：它不进 `items[]`，因此不计站数、不计停留、不参与"这一天有几站"。

### 3.2 规则（`src/domain/validation.ts`）

| 现有 | 改成 |
|---|---|
| `EMPTY_DAY`：`items.length === 0` | items 为空**且**没有 transits 才算空（severity 仍 info） |
| `DAY_OVERLOADED`：总时长 > 10h | 分两种口径：**转场主导**（移动时长里转场 ≥ 80%）→ 「第 1 天在路上约 12.6 小时，单日驾驶偏长」，建议动作换成「中途加一晚 / 两人换着开」；否则保持原措辞 |
| `MISSING_ROUTE`：相邻两项缺 leg | 新增 `MISSING_TRANSIT`：某天标题声明了跨城、或相邻两天端点不在同一城市，却没有 transit / leg —— 这就是现在客户端从标题猜数字的那条路径，改成有据可依 |
| `ROUTE_STALE` / `ROUTE_FAILED` | 对 transit 同样判定（同一个 code，`relatedIds` 指向 transit.id） |
| 站数、停留、节奏（pace） | 只统计 items —— 转场天然不计 |

### 3.3 视图与界面

- `TravelView` 的 `day` 增加 `transits: TransitView[]`（含端点名称/坐标、里程、时长、时刻、新鲜度、来源）。
- **行程页**：有转场的日子，在天头下面先渲染一张**转场卡**（不是站点卡）：
  ```
  D2 · 09-25 周五   西安 → 成都｜翻秦岭 723km
  ┌───────────────────────────────────────────────┐
  │ 🚗 驾车 · 723 km · 8 小时 12 分                │
  │ 08:00 从西安出发 → 16:12 抵达成都               │
  │ 路线来自高德 · 3 天前          [重算] [改时间]  │
  └───────────────────────────────────────────────┘
  18:30  宽窄巷子景区   ← 到达之后的安排，照旧是站点卡
  ```
  纯赶路日就**只有这张卡**，不再有"这一天还没有安排"。
- **天头**：`行驶 12 小时 38 分 · 1077 km · 转场 · 2 站`（站数只数真正停留的地点）。
- **日期目录**：距离/强度直接用转场里程（现在是退回标题估算，将来是真数据）。
- **地图**：转场画**真实路线**（`steps` 或重新规划得到的折线），不再是两点之间的虚线；端点用**另一种形状**（方形/空心水滴，标「出发」「抵达」）以便和"要游玩的站"区分；跨午夜时到达点归次日。
- **详情面板**：端点若不是游玩站点，不显示「停留 / 时间」，改成「途经 / 抵达」。
- **删除的旧行**：「跨城交通未记录 · 里程按当天标题估算」这条临时行被转场卡取代（没有转场时保留它作为"待补"状态，并给出「记为转场」按钮）。

### 3.4 怎么产生转场（三条路径，都不靠猜）

1. **从标题一键升级**（迁移你现有行程的路）：客户端已经在用 `parseTransferTitle` 解析 `西安 → 成都｜翻秦岭 723km`，也已经知道相邻两天的端点地点（`buildTransfers`）。新增动作「记为转场」→ 由 Host 写成 `transit`（`source: 'title'`，里程用标题里的数），随后可用「重算」变成真实路线。
2. **规划产生**：新工具 `travel_day_set_transit(dayId, from, to, mode?)` —— 调现有 `travel_route_plan`（高德 CLI / Web 服务）拿到距离、时长、steps，写进当天并盖上 `source`/`freshness`。同时 `travel_project_patch` 增加 `set-day-transit` / `remove-day-transit` 两个 op。
3. **导入时提示**：新行程若某天没有 items 而标题写了 A → B，Host 在 view 里给出**建议**（不落盘、不编造数字），前端显示「这段路还没记录 · 记为转场」。

### 3.5 兼容与迁移

- 读旧文件（`schemaVersion: 1`）**不改写数据**：`transits` 缺省为空，客户端继续用现有的标题兜底行 —— 行为与今天一致。
- 用户/Agent 一旦写出 transit，就升级为真实数据；`schemaVersion` 升到 2 只在**写入**时发生。
- 导出：Markdown 行程单把转场渲染成 `- 🚗 西安 → 成都 · 723 km · 8h12m`；JSON 原样保留。
- 统计口径（站数、停留、游玩日）天然把转场排除；`dayIntensity` 已经按"当天公里数"算，加上转场里程后赶路日的条形会正确地长起来。

## 四、备选方案与取舍

| 方案 | 做法 | 为什么不选 |
|---|---|---|
| **A. 只放宽 `EMPTY_DAY`** | 允许空白天，路只写在标题里 | 地图画不出、里程无法参与统计/告警，等于把问题留在标题文本里 |
| **B. `item.kind = 'transit'`** | 给 item 加个"只是路过"的类型 | 仍然**必须绑一个地点**（你的原话），而且站数/缩略图/停留那套管线还得为它开特例；比 A 好，但仍没解决"端点不是游玩地点" |
| **C. 把行程重构成"移动 + 停留"的连续序列**（长期最干净：一天只是日期窗口，leg/transit 连接的是序列里的节点，可以跨天） | 彻底的模型 | 会改动 `items[]` 的语义与文件结构，是一次大迁移；**本方案的 transit 是它的踏脚石**：先让"跨城的移动"能独立存在，将来把 leg 也统一到同一张图上 |

## 七、实施记录（0.11.0 → 0.11.1）

用户批准全部四点建议（多段转场数据支持、端点可只有名字、迁移默认不猜、赶路日派生显示不新增日类型字段）。

### 已实现（P1 全部 + P2 的真实路径）

**领域**
- `TripDay.transits?: TripTransit[]`；`TransitEnd = { placeId?, label }`；`schemaVersion` 1 → 2，`trip-store` 改为接受 `[1, 2]`，版本 1 的文件照常读、只在写入时升级。
- patch op：`set-day-transit` / `remove-day-transit`（端点只给 `placeId` 时名称自动从地点库补全；未知地点、无名端点、未知天都各自报错）。
- 校验：`EMPTY_DAY` 改为"既没有站点也没有转场"；新增 `MISSING_TRANSIT`（info，标题声明了跨城但既无转场也无 ≥1km 的 leg）；转场与 leg 一起判 stale/failed（每天一条）；转场主导的日子改说「在路上约 12.6 小时（1077 km），单日驾驶偏长」，建议动作换成「中途加一晚住宿／两个人换着开」。
- `claimsHop(title)`（仅检测箭头）放在领域里；客户端那份 `parseTransferTitle` 仍负责取里程——两份各自可测，互不依赖。

**Host**
- `TravelView.days[].transits`（端点的名称/坐标、里程、时长、时刻、polyline、来源、stale）。
- `TravelService.setDayTransit()`：两端有坐标时优先走 **Web 服务驾车 API**（`/v5/direction/driving`，`show_fields=cost,polyline`，新增 `drivingRouteOverRest`），拿不到 Key 时退回高德 CLI；两者都不可用或调用方声明 `plan:false` 时，用调用方给的数字并标 `stale` + `source:title`。到达时刻由 `departAt + duration` 推出。
- 工具 `travel_day_set_transit`；`patch-input` 增加两个 op 的校验。

**客户端**
- 转场卡（路线、里程/时长、出发→抵达、`按标题估算`/`路线待更新`/`路线失败` chip、「用高德重算」「删除转场」）。
- 天头加「转场」，`dayFacts` 把转场里程与时长并入当天数字（日期目录随之从 `≈723 km` 变成真数据）。
- 「跨城交通未记录」行升级为「**记为转场**」：一次 patch 直接写入（`transitOpFromTransfer`），另有「让 Agent 重算」走工具。
- 地图：转场画**实线**（有 polyline 就是真实路径，否则两端直线），未与站点重合的端点用**方块**标记并带「出发/抵达：名称」提示。
- 兼容：视图缺少 `transits` 时面板不崩（页面可能先于 Host 重启刷新）——这条是实施中真踩到的崩溃，已加测试。

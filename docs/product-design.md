# 产品设计：旅程台（Travel Canvas）

> 状态：初始设计基线  
> 面向场景：个人 / 情侣自由行  
> 首发地图范围：中国大陆，以高德 CLI 为首个 Provider  
> 记录日期：2026-09-14

## 1. 产品目标

旅程台不是一次性生成攻略的聊天机器人，而是 DSH 中由用户和 Agent 共同维护的结构化旅行工作台。

核心承诺：

1. 将模糊旅行意图逐步收敛成可执行的逐日行程。
2. 地点、路线、时间和预算可以被查询、校验和解释。
3. 用户修改一个约束时，仅调整受影响且未锁定的内容。
4. 对话、右侧栏和模型 Tool 操作同一个 Trip Project。
5. 事实、估算、建议和未知项必须明确区分。

北极星指标：用户可以在 10 分钟内，从一句自然语言需求得到一份可查看路线、可局部修改、带风险提示的行程草案。

## 2. 核心用户故事

### 2.1 创建旅行

用户可以说：

> 我和伴侣下个月从上海去杭州三天，预算 5000 元，喜欢咖啡和慢节奏，不想频繁换酒店。

插件提取已知约束，只追问阻塞规划的少量信息，然后创建 Trip Project。

### 2.2 研究地点

Agent 使用高德 CLI 搜索 POI，并把候选地点标准化为项目内的 Place。地点至少保留名称、地址、坐标、电话、类别、高德 POI ID、查询时间和来源。

### 2.3 生成逐日行程

Agent 根据区域、开放时段、用户节奏和交通成本安排每日地点。每一段移动都应有明确的出行方式、距离和预计耗时。

### 2.4 增量调整

用户可以说：

- “第二天不要去商场。”
- “把这个咖啡馆换到下午。”
- “清水寺必须保留。”
- “下雨时改成室内方案。”

Agent 必须生成结构化 patch，只修改受影响的未锁定项目，并返回变更摘要。

### 2.5 校验和就绪

行程从草案进入就绪状态前，至少校验：

- 同一时段是否重叠；
- 相邻地点是否有可行路线；
- 交通时间是否已计入；
- 每日强度是否超过偏好；
- 预算是否明显超限；
- 关键地点是否缺少确认信息；
- 锁定项目是否被意外修改。

## 3. 核心产品对象

### 3.1 Trip Project

Trip Project 是最终事实来源，聊天记录不是。

```text
TripProject
├── 基本信息：标题、目的地、时区、日期、同行人
├── 偏好：兴趣、节奏、饮食、体力、交通偏好
├── 约束：预算、必去、避开、固定预约
├── Places：标准化地点库
├── Scenarios：主方案、轻松版、雨天版等
├── Days：逐日时间轴
├── Legs：地点之间的交通段
├── Budget：估算与已确认支出
├── Alerts：错误、警告和建议
├── Locks：用户锁定项
└── Revisions：变更历史
```

### 3.2 方案分支

首版支持一个主方案和若干分支：

- 经典版；
- 慢节奏版；
- 雨天版；
- 预算优先版。

分支应共享地点事实，但拥有独立的日程排序、交通段和预算估算。

### 3.3 状态

```text
idea -> drafting -> checking -> ready -> traveling -> archived
                    \-> needs-attention
```

- `idea`：只有意图和少量约束。
- `drafting`：Agent 正在研究和编排行程。
- `checking`：正在补路线、预算和冲突校验。
- `needs-attention`：存在用户必须处理的阻塞项。
- `ready`：关键路线已校验，阻塞项清零。
- `traveling`：旅途中使用，突出“接下来”和临时调整。
- `archived`：旅行结束后只读保存。

## 4. 功能模块

### 4.1 Travel Brief

创建项目时维护一张简短旅行简报：

- 出发地与目的地；
- 日期与可用天数；
- 同行人；
- 总预算与货币；
- 兴趣标签；
- 每日强度；
- 必去 / 不去；
- 固定预约；
- 住宿策略；
- 交通偏好。

原则：优先从对话推断，不要求用户先填写长表单。

### 4.2 地点研究

- 关键词搜索；
- 城市范围搜索；
- 以酒店或当前地点为中心的周边搜索；
- 候选地点比较；
- 加入旅行地点库；
- 标记“候选 / 已采用 / 已排除 / 已锁定”。

### 4.3 路线规划

- 步行、公交、骑行、驾车；
- 驾车途经点；
- 距离、预计时长、费用和步骤；
- 日内相邻地点逐段规划；
- 地理折返检测；
- 单日总移动时间计算。

公交路线必须按城市逐段查询；不可把多城市或跨城交通伪装成本地公交结果。

### 4.4 行程编排

- 上午 / 下午 / 晚间或精确时间轴；
- 拖动排序；
- 锁定地点、时间段或整天；
- 替换地点；
- 自动补齐交通段；
- 仅重新优化未锁定内容；
- 生成方案分支；
- 撤销最近一次结构化 patch。

### 4.5 风险与待确认

告警分三级：

- `error`：必须处理，例如时间重叠、路线不可用；
- `warning`：可能影响执行，例如通勤过长、地点信息陈旧；
- `info`：优化建议，例如附近存在更合适的备选地点。

每个告警必须包含关联对象、原因、证据和可执行动作。

### 4.6 预算

首版只做估算与人工确认：

- 门票；
- 市内交通；
- 住宿占位；
- 餐饮日预算；
- 其它费用；
- 每日及全程汇总。

不得把粗略估算展示成实时价格。

### 4.7 导出

MVP：

- Markdown 行程单；
- JSON 项目备份。

后续：

- 日历文件；
- 可打印 PDF；
- 分享链接；
- 离线旅途中模式。

## 5. 模型 Tools 建议

所有 Tool 使用全局唯一的 `travel_` 前缀：

| Tool | 职责 |
|---|---|
| `travel_project_create` | 创建项目并保存旅行简报 |
| `travel_project_read` | 读取完成当前任务所需的最小项目切片 |
| `travel_project_patch` | 带 revision 和锁定校验地增量修改 |
| `travel_place_search` | 经高德 CLI 搜索和标准化地点 |
| `travel_route_plan` | 经高德 CLI 查询一段路线 |
| `travel_day_rebuild_legs` | 重建一天中相邻地点的交通段 |
| `travel_itinerary_validate` | 检查时间、路线、预算和锁定约束 |
| `travel_scenario_branch` | 从指定 revision 创建方案分支 |
| `travel_project_export` | 导出 Markdown 或 JSON |

设计规则：

1. Tool 负责事实查询、确定性计算和持久化；模型负责理解与取舍。
2. 写操作必须携带 `expectedRevision`，避免并发覆盖。
3. Tool 返回最小 JSON，不返回 Cordis Service、Context 或 Session 对象。
4. 每次写操作返回变更摘要、受影响对象和新增告警。
5. 坐标统一声明为 GCJ-02，不允许静默混用 WGS-84。

## 6. DSH 交互面

### 主入口：右侧 Sidebar

右侧栏是当前项目的伴随工作面：用户一边与 Agent 对话，一边查看地图、逐日路线、地点卡片和告警。详细设计见 [right-sidebar-ux.md](./right-sidebar-ux.md)。

### 对话内反馈

Tool 调用和 Agent 回复应提供轻量摘要：

- 找到了多少候选地点；
- 更新了哪一天；
- 路线总时长变化；
- 新增或解决了哪些告警；
- “在右侧栏中查看”的操作入口。

对话不重复渲染完整旅行工作台。

### 设置页

最终原生 Client 插件应提供设置页，用于：

- 高德凭据引用；
- CLI 可执行文件位置或自动发现策略；
- 默认货币；
- 默认旅行节奏；
- 缓存和自动启动策略；
- 隐私与数据清理。

## 7. MVP 边界

### 必须完成

- 一个 Trip Project 的创建、读取和增量修改；
- 高德 CLI POI 搜索和路线查询；
- 逐日行程、地点卡片和路线段；
- 右侧栏普通与全屏布局；
- 地图标记与卡片联动；
- 锁定、告警和 revision；
- Markdown / JSON 导出；
- Host、Client、CLI 的可逆生命周期；
- 深色、浅色、窄屏和键盘操作。

### 明确不做

- 自动支付、机酒下单或取消；
- 实时票价承诺；
- 复杂多人协作；
- 社区攻略内容平台；
- 把高德未提供的数据伪装成已核实事实。

## 8. 后续里程碑

1. **动态原型**：用模拟项目验证右侧栏类型注册、打开、关闭和全屏切换。
2. **高德网关**：实现 CLI 生命周期、参数化执行、JSON 校验和错误映射。
3. **原生 Host**：Trip Project、Tools、持久化、revision 与锁定。
4. **原生 Client**：地图、时间轴、地点卡片、告警与设置页。
5. **集成验证**：真实 DSH profile、tarball、浏览器和清理验证。

## 9. 验收标准

一个 MVP 只有在以下场景完整通过时才算可用：

1. 用户从一句自然语言创建三日旅行。
2. Agent 经高德 CLI 加入至少五个真实地点。
3. 每个相邻地点生成路线段。
4. 右侧栏能在地图和时间轴中同步选中地点。
5. 用户锁定一个地点后，重排不会移动它。
6. 制造时间冲突后能产生告警并定位到卡片。
7. 收起、切换会话、重新打开时不会泄漏监听器或 CLI 进程。
8. 导出的 Markdown 与当前 revision 一致。
